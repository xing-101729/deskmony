# S6 HLD:崩潰復原(對帳 + 人工分流)

> 階段:**Phase 1**(最後一份)｜對應 L1:**D1–D4**｜上層:[L2 §3](../LAYER-2-design-spec.md)、[DECISIONS §D](../DECISIONS.md)
> 前置:[S3b](./cost-governor_hld.md)(資源回收/blocked 語意)、[S7](./auto-mode-and-yolo_hld.md)(暫態消失)、[S11](./notification_hld.md)(掛起狀態)
> **核心立場(D1)**:崩潰復原的本質是「**對帳你的帳本 + 人工分流在途工作**」,**不是 replay**——最貴的東西(agent 累積的推理/context)活在**後端 agent 行程**裡,不在你的 DB。你 replay 自己的事件,重建的是帳本,不是 agent 的腦。

---

## 0. 現況(已查證)

**完全沒有任何崩潰對帳/恢復邏輯**。core 啟動流程只做:載入 config → seed profile → 開 gateway。

⇒ 崩潰後 DB 的 `sessions` 表會留下狀態為 `busy` / `waiting` 的**孤兒紀錄**(子程序早已隨 core 一起死),**沒有任何東西去處理它們**。UI 會顯示一堆「正在忙碌」但其實已死的 session。

---

## 1. 職責邊界

**負責**:
- **啟動對帳**:找出 DB 與現實不符的紀錄(孤兒 session)、標記真實狀態。
- **優雅關閉收尾**:正常關閉時主動標記,讓對帳只處理真正的異常(§2.1)。
- **復原視圖**:列出中斷的任務 + 各自的髒 worktree,供人**逐一分流**(繼續 / 接手 / 重跑 / 放棄)。

**不負責**:
- ❌ 自動續接 mid-flight 任務(**D3 明令禁止**,見 §3)。
- ❌ 重建 agent 的推理狀態(做不到,D1)。
- ❌ 完整 event sourcing(D1 否決)。
- ❌ **Mailbox 持久化的實作**——決策 D4 不變,但**實作時機移交 S2(Phase 2)**,見 §4。

---

## 2. 啟動對帳(D2)

```
core 啟動
  → 掃 sessions 表,找「未被乾淨收尾」的紀錄(§2.1)
  → 這些子程序必然已死(隨 core 一起崩潰)
  → 標記為 interrupted,記錄崩潰時間
  → 依後端的 session 持久化能力決定提供哪種恢復(§2.2)
```

### 2.1 崩潰 vs 正常關閉:靠「有沒有被乾淨收尾」(S6 grill 定案)

**問題**:若只憑「殘留 `busy` 狀態」判定崩潰,則**每次正常關閉也會看到復原視圖** → 它很快變成你按 X 略過的雜訊,真正的崩潰也被一起忽略(與 S11「保住通知可信度」是同一種失敗模式)。

**定案:優雅關閉時主動收尾**——正常關閉走 shutdown handler:dispose 子程序、把 session 標成 `closed`、清除 auto/YOLO 暫態。啟動對帳**只處理沒被收尾的**紀錄。

- **「沒被乾淨收尾」即崩潰的定義**——強制關機/斷電時 handler 跑不到,而那本來就是崩潰,分類正確。
- **幾乎免費**:shutdown handler 本來就該 dispose 子程序,否則會留殭屍行程。
- **不做 heartbeat/PID 檔**:其主要價值在「多實例/遠端偵測」,對單機桌面工具是過度工程。

### 2.2 兩種恢復,必須分別命名(S6 grill 定案)

**問題**:「續接」一詞掩蓋了兩種**完全不同的承諾**。關鍵事實:adapter spawn 的是**子程序**,隨 core 一起死 ⇒ 它記憶體裡的 context 也沒了。**除非後端自己有磁碟持久化**(如 Claude Code 的 `--resume`),否則「重連」根本沒東西可連。

| UI 名稱 | 實際做的事 | 承諾 |
|---|---|---|
| **繼續(保有記憶)** | 重連後端**磁碟持久化的既有 session** | agent **記得**先前脈絡 |
| **接手(讀摘要重啟)** | 開**新** session,注入摘要/歷史 | agent 的腦是新的,只是**讀過筆記** |

- 能力表應標明「**該後端支援哪一種**」,而非籠統的「可否續接」。各後端到底有無磁碟持久化 session,**L4 需逐一查證**。
- **PTY**:兩種都不支援 → 誠實顯示「已消失」。
- 理由:若都叫「續接」,使用者會以為 agent 記得、實際只讀了摘要,進而**做出錯誤的分流決定**(以為它記得就不補充脈絡)。**能力可以有限,但承諾必須精確**——與 S4(驗收是快篩)、S1(shell 擋不住)、S3b(反應式)一貫作風。

**暫態一律不復活(fail-safe,與 S7 §6 一致)**:
- session auto / YOLO 暫態 → **消失**,回落 profile 預設(S7 §2.1 已確保 profile 不可能是 YOLO)。
- 掛起的 `waiting-permission` → 重啟後仍是等待中,但**需重新發出 escalate**(原 requestId 已隨子程序消滅)。

## 3. 任務分流:永不自動續接(D3)

**為何禁止自動續**:一個**丟了 context 的 agent 自動接著跑**,是「重做 / 半做 / 毀壞」的溫床——它不知道自己做到哪,可能重複已完成的動作、或在半完成的檔案上疊加。

```
復原視圖(RecoveryView)
├─ 任務 A  [in-progress]  worktree: 3 個檔案未提交   → [接手] [重跑…] [放棄]
├─ 任務 B  [waiting-perm] worktree: 乾淨            → [繼續] [接手] [放棄]
└─ 任務 C  [merging]      ⚠️ 崩潰於合併中           → [檢查 git 狀態]
```

- 每列顯示:任務狀態、worktree 髒污程度(`hadUncommittedChanges` **既有機制**)、崩潰時間、**該後端支援哪種恢復**(§2.2)。
- **人逐一決定**,系統不預設任何動作。
- **worktree 一律保留**——與 S3b §4「回收 ≠ 丟棄」一致。
- **`merging` 中崩潰是最危險的**(git 可能處於中間狀態)→ 特別標示,引導人先檢查 git 狀態,**不自動修復**。

### 3.1 「重跑」對髒 worktree 的處理(S6 grill 定案)

崩潰的 worktree 常有 agent 改到一半的檔案。**「重跑」必須先解決它**:

| 做法 | 判定 |
|---|---|
| 在現有髒 worktree 上直接重跑 | ❌ agent 面對一堆自己不記得改過的檔案,可能重複修改、疊加出爛狀態——**正是 D3 禁止自動續接的同一個理由**,只是換人觸發 |
| 直接重置到乾淨再重跑 | ⚠️ 語意清楚但**會丟掉半完成的工作**(可能有價值)|
| **重跑前強制人類先處理髒污** | ✅ **採用** |

- **重跑**預設要求 worktree 乾淨。若髒 → 先顯示 diff,人選擇 **保留(commit 到 wip 分支)** 或 **丟棄**,才能重跑。
- 提供「**丟棄並重跑**」快捷,但**必須明確確認**(它會刪掉工作)。
- **絕不**默默在髒 worktree 上重跑。
- 與整份設計「**破壞性動作必須是有意識的**」(C4/C6、S7 窄規則)一脈相承。

## 4. Mailbox 持久化 → **移交 S2(Phase 2)**(S6 grill 定案)

**決策 D4 本身不變**(Mailbox 必須持久化),但**實作時機歸 Phase 2 的 S2**,S6 不扛。

理由:
1. **Phase 1 是單 agent,沒有隊友訊息可掉**——在 Phase 1 做,是為一個**還不存在的功能**做崩潰防護。
2. **與 S4 的先例完全一致**:S4 的硬擋閘也因為「切片沒有 agent 可擋」而延到 Phase 2。同一把刀,同樣的邏輯。
3. Mailbox schema 與 MessageBus 的投遞策略(idle 注入 / busy 排隊 / 不在線落地)**耦合很緊**,分開做容易定錯 schema。

---

## 5. 稽核 log(D5)

保留**便宜的** append-only log,只記:**訊息 + 權限決策 + enforcement 事件**(底座 `AuditLog` 已定義)。

- 用途:除錯、安全稽核、S3b 的成本歸因還原。
- **明確不做**:不把全系統狀態重架成事件流(D1)。

---

## 6. 失敗模式

| 情境 | 行為 |
|---|---|
| 對帳時 DB 損毀 | 啟動失敗並明確報錯(同 config 損毀的既有作風),**不帶著壞資料啟動**。 |
| 後端宣稱可「繼續」但實際連不上 | 恢復失敗 → 標記 error,退回分流視圖讓人改用「接手」/重跑/放棄。 |
| worktree 已被外部刪除 | 標示「worktree 遺失」,只提供「放棄」。 |
| 正常關閉時 shutdown handler 失敗 | 該 session 未被收尾 → 下次啟動視為崩潰(**保守方向正確**:寧可多問一次,不可漏掉真崩潰)。 |
| 崩潰於 `merging` 中 | 特別標示;**不自動修復 git 狀態**(可能需要 `git merge --abort`,由人決定)。 |
| 大量孤兒 session(如 20 個) | 對帳批次處理;復原視圖分頁,不阻塞啟動。 |
| 使用者忽略復原視圖直接開新任務 | 允許——舊的留在 blocked,不強制先處理。但**應持續可見**(同 S7 auto 標記的作風),避免遺忘。 |
