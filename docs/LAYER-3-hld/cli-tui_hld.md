# 全螢幕 TUI(`deskmony tui`)HLD

> 狀態:設計定案(2026-09-10)。分支 `feat/cli-tui`,基於 `feat/cli`。
> 前置文件:[`cli_hld.md`](cli_hld.md)——本文延續它的 §1(CLI 不是第二個
> orchestrator)、§6(權限提示)、§7(跨平台)三條紀律,不重複論證。

## 0. 先更正一件事

`cli_hld.md` §3 當初把全螢幕 TUI 排除在 Phase 1 外,理由寫的是:

> 全螢幕 TUI 在 `cmd.exe` 上的相容性問題(codepage、alternate screen buffer、
> 滑鼠序列)是另一個工程。

**那個理由查證後不成立。** 2026-09-10 用兩支探針對真實終端量測(不是目測,見
§1),結果是 alternate screen、CJK 全形寬度、框線字元、Braille、resize 事件、
方向鍵原始位元組**全部正常**,而且測試環境還不是 Windows Terminal(`WT_SESSION`
未設定),是傳統 conhost。

當初的判斷是基於「聽說 cmd.exe 很爛」這種印象,不是量測。排除 TUI 這個決定
在 Phase 1 仍然正確(範圍控制),但**寫下的理由是錯的**,在此更正——否則它會
變成下一個人不敢做 TUI 的依據。

真正該擔心的只有一項,而且不是相容性問題,是排版問題:**emoji 寬度不一致**
(§1.3)。

## 1. 量測結果(先量再設計)

### 1.1 手法

用 DSR(`ESC[6n`)問終端機「游標現在在第幾欄」,寫入前後相減 = 那段字元**實際
佔用的欄數**。這比截圖目測可靠——TUI 排版壞掉幾乎都壞在「以為佔 1 欄、實際
佔 2 欄」,而那種一欄之差在截圖上看不出來。

輸入面(resize / 按鍵)無法用截圖驗證,改用 `node-pty` 開真的 ConPTY,程式化
送按鍵與改尺寸,由受測方回報收到什麼。

### 1.2 輸出面(真實 conhost,120×30,`TERM` 未設定,`WT_SESSION` 未設定)

| ASCII 10 字 | 10 欄 ✅ |
| CJK 全形 5 字「中文字測試」 | **10 欄** ✅ |
| CJK 混 ASCII「中文AB中文」 | **10 欄** ✅(2+2+1+1+2+2) |

### 1.2.1 這張表證明了什麼、沒證明什麼

DSR 量到的是**終端機帳面上認為那個字佔幾欄**。它不等於「字型真的畫得出那個
字形」——字型缺字時終端機照樣記 1 欄,但畫出來是空白或豆腐框。兩者要分開講:

- **帳面寬度**:上表全部,已量測。
- **字形實際渲染**:只有細框線 `┌─┐│└┘` 經過目視確認(探針視窗的外框正常
  畫出來)。粗框線、圓角、區塊、陰影、Braille、箭頭**只有帳面寬度,沒有目視
  確認**——Cascadia Mono 與 Consolas 都涵蓋這些區段,理論上沒問題,但這是
  推論不是量測。

**T1 的驗收要補一次目視確認**(§10.2),把 §3 實際用到的整組圖示字元畫在真實
終端機上截圖。在那之前,設計裡任何依賴粗框線/圓角的地方都要能退回細框線。

另外,`cli_hld.md` §7 寫的「一律只用 ASCII 當結構符號」是 CLI 的紀律,**TUI
刻意偏離**:行導向輸出混進使用者自己的 shell 歷史,保守是對的;全螢幕 TUI
獨佔畫面、且已經量測過寬度,用框線字元換來的可讀性值得。CLI 那邊不改。

### 1.3 唯一的真陷阱:emoji 寬度不一致

`🚀` 佔 2 欄、`🛡` 佔 1 欄——同樣是 emoji,終端機算出來的寬度不一樣。原因是
`🛡`(U+1F6E1)的 East Asian Width 屬性是 Neutral(它是「文字預設」的 emoji),
規範上算 1 欄,但**字型往往畫成 2 欄寬**。畫出來的寬度與終端機記帳的寬度一旦
不一致,那一整行之後的所有內容就錯位,而且錯位會一路傳染到重繪為止。

**紀律:TUI 的結構性元素一律不用 emoji。** 狀態、圖示、分隔一律用已量測過
穩定佔 1 欄的字元集(`●○◐⚠✓✗▸▾│─└├`)。agent 自己吐出來的 emoji 屬於**內容**,
照原樣顯示即可——內容錯位只影響那一行,結構錯位會毀掉整個版面。

### 1.4 輸入面(node-pty / ConPTY,程式化送鍵)

resize 三次(100×40 → 65×22 → 140×50)**全部觸發** `process.stdout.on("resize")`,
且 `columns`/`rows` 同步更新。

按鍵原始位元組:

| 鍵 | 位元組 | 鍵 | 位元組 |
|---|---|---|---|
| ↑↓→← | `1b 5b 41/42/43/44` | Tab | `09` |
| Shift+Tab | `1b 5b 5a` | Enter | `0d` |
| **Esc** | **`1b`** | Backspace | `7f` |
| **Ctrl+C** | **`03`** | Ctrl+A / Ctrl+D | `01` / `04` |
| PageUp / PageDown | `1b 5b 35/36 7e` | Home / End | `1b 5b 48` / `1b 5b 46` |
| `a` | `61` | `中` | **`e4 b8 ad`**(UTF-8 3 bytes) |

三個直接影響設計的結論:

1. **Ctrl+C 在 raw mode 是一個位元組,不是訊號**——這與 `cli_hld.md` §7 和
   `apps/cli/src/bin.ts` 註解說的一致,TUI 必須自己處理。
2. **裸 Esc 就是 `1b`,與跳脫序列的開頭完全無法區分**。必須靠逾時分辨
   (見 §6.2)。
3. **中文輸入是多位元組**,chunk 邊界有可能切在一個字中間。stdin 一定要走
   `StringDecoder`,不能對每個 chunk 直接 `buf.toString()`。

## 2. 這個 TUI 存在的理由(不是「全螢幕版的 chat」)

如果 TUI 只是把 REPL 畫進框線裡,它不值得做——`deskmony chat` 已經夠用,而且
在 pipe、dumb terminal、ssh 沒有 TERM 的情況下還更可靠。

TUI 能做、而行導向 REPL **結構上做不到**的事只有一件:

> **同時盯住多個 agent,並且不論待決的權限請求來自哪一個 session,都能立刻
> 看到它。**

這正是 Deskmony 的產品命題(一整隊 agent 無人值守跑數小時)在終端裡的缺口。
在 REPL 裡,你正在看 session A 的輸出時,session B 跳出來的權限請求**完全
看不見**——而 `cli_hld.md` §11 查證過:無人在場時待決請求**不設逾時**,session
會一直停在 `waiting`。也就是說 B 會安靜地卡住,直到你想起來去看它。

所以這個 TUI 的中心不是對話框,是**跨 session 的權限佇列**(§4)。版面的其餘
部分都是為了讓人有足夠上下文去做那個決定。

`deskmony chat` **不會**被取代。兩者並存,分工:`chat` 給單一 session 的專注
工作與任何非互動情境;`tui` 給「看著一隊人幹活」。

四個區域,職責固定:

| 區域 | 內容 | 為什麼在這 |
|---|---|---|
| **Sessions**(左,固定 22 欄) | 全部 session、狀態圖示、標題 | 多 agent 是產品命題,不能藏在子指令後面 |
| **Transcript**(中,填滿) | 焦點 session 的串流輸出 | 做決定需要的上下文 |
| **Alert bar**(下,權限有待決才出現) | 跨 session 的待決權限數 + 是哪幾個 | §2 的核心。**永遠可見,不受目前焦點影響** |
| **Status bar**(底,固定 1 列) | 今日花費/上限、斷路器狀態、按鍵提示 | 成本斷路器是三個斷路器裡唯一會安靜跳掉的 |

狀態圖示(全部量測過佔 1 欄):`●` busy · `○` idle · `⚠` waiting · `✗` error ·
`◐` 連線中 · `·` closed。**不用顏色當唯一訊號**——單色終端與色盲都要能分辨,
所以圖示本身就要有區別。

### 3.1 尺寸退化

| 寬 × 高 | 行為 |
|---|---|
| ≥ 100 × 24 | 完整版面(如上) |
| 80–99 欄 | Sessions 窗格縮到 16 欄,只顯示圖示 + 截斷標題 |
| 60–79 欄 | Sessions 窗格收合成一列「3 sessions · [s] 展開」 |
| < 60 欄 或 < 16 列 | **不畫版面**,顯示一行「終端機太小(目前 52×14,需要至少 60×16)」並持續監聽 resize,一夠大就自動進版面 |

最後一列很重要:不是報錯退出,是等。使用者拉大視窗就繼續——因為 resize 事件
已經量測過會觸發(§1.4)。

## 4. 權限佇列(這份設計的核心)

### 4.1 觸發

任何 session 的 `permission-request` 事件抵達 → 進入佇列 → alert bar 立刻更新
(不論目前焦點在哪個 session)。`permission-resolved` 推播抵達 → 從佇列移除
(可能是別的 client 處理掉的,或政策引擎自動判定,見 `cli_hld.md` §11)。

### 4.2 逐一處理的畫面

```
╭─ 權限請求 1/2 ─ QA · session 3ee96883 ──────────────────────────────╮
│                                                                     │
│  工具   Bash                                                        │
│  指令   rm -rf node_modules/.cache                                  │
│  目錄   D:\AgentTeam\Deskmony\.worktrees\task-41                    │
│                                                                     │
│  [a] 允許一次    [d] 拒絕    [A] 永遠允許(最窄規則)                 │
│  [n] 下一筆      [Esc] 稍後再說                                      │
╰─────────────────────────────────────────────────────────────────────╯
```

紀律,全部沿用 `cli_hld.md` §6,一條都不放寬:

- **渲染 `input`,不是 `description`。** `cli_hld.md` §13.3 查證過
  `description` 只有 `"Write file"` 這種毫無資訊量的字串,真正要看的東西全在
  `input` 裡。只印 `description` 等於把安全罩最後一道人工關卡廢掉。
- `permission.resolve` 的 **`sessionId` 必填**——TUI 天然是多 session,這裡
  尤其不能靠 `requestId` 反查(它只保證單一 session 內唯一)。
- **`[A]` 只寫最窄的規則**(`commandEquals` / `pathUnder`),與桌面
  `PermissionModal.tsx` 的預設候選一致。

### 4.3 escalate-strong 的差別待遇

`strong === true`(hard-deny 在「本機 + 有人在場 + 未開 auto」時被降級而來)的
請求,畫面必須**明顯不同**,而且:

```
╭─ ⚠ 高風險 ─ 這個操作命中了硬性拒絕清單 ──────────────────────────────╮
│                                                                      │
│  工具   Bash                                                         │
│  指令   git push --force origin master                               │
│  命中   危險 git 操作(強制推送)                                      │
│                                                                      │
│  這類操作預設一律拒絕。要放行請完整輸入 yes 後按 Enter:              │
│  > ▏                                                                 │
│                                                                      │
│  [Esc] 取消(維持拒絕)          ※ 這類請求不提供「永遠允許」          │
╰──────────────────────────────────────────────────────────────────────╯
```

- 用紅色 **加上** `⚠` 圖示與不同的框線字元(`╭╮╰╯` 圓角 vs 一般的 `┌┐└┘`)——
  單色終端也要看得出差別。
- **不提供 `[A]`**。core 本來就會剝掉 strong 請求的 `rememberRule`(C4 紀律③),
  UI 不提供只是不要讓人以為有這個選項。
- **要求完整輸入 `yes`**,不是單鍵。單鍵確認在一個「連按 a 快速清佇列」的
  介面裡太容易誤觸——而這正是誤觸代價最高的一類。

### 4.4 刻意不做的:批次核准

不提供「全部允許」。逐一是設計,不是遺漏——一個能一鍵放行整個佇列的按鈕,
等於把安全罩的最後一關變成橡皮圖章。要無人值守就用
`--permission-mode auto-accept-edits`,那條路徑會經過 core 的政策引擎,
留下稽核紀錄,而且擋得住 hard-deny。

## 5. 技術選型

### 5.1 用 Ink,並誠實記下它的代價

| 選項 | 判斷 |
|---|---|
| **Ink**(React for terminals) | ✅ 採用 |
| 手刻 ANSI + 自己做 diff/layout/focus | ❌ 光做好版面協調與重繪就是 3000+ 行,而且是別人早就解過的問題 |
| blessed / neo-blessed | ❌ 久未維護 |
| terminal-kit | ❌ API 面過大,社群動能不如 Ink |

理由:這個 repo 的 `apps/desktop` 已經是 React 18,團隊心智模型直接沿用;Ink
也是 Claude Code 與 gemini-cli 的選擇,踩過的坑有人踩過了。

**代價要說清楚**:Ink 會帶進 `react`、`react-reconciler`、`yoga-layout`(WASM)
與數十個 transitive 相依。這個 repo 在 2026-09-04 才剛清掉 68 個 advisory,
新增這麼一大塊供應鏈不是零成本。這是有意識的取捨,不是沒注意到。

### 5.2 但 `deskmony run` 不准因此變慢

`apps/cli` 目前的相依只有 `ws` + 三個 workspace 套件,`deskmony run` 啟動很快,
而它是會被塞進 CI 與腳本的那個指令。

**紀律:Ink 只能在 `tui` 這個 command 的模組裡被 `await import()`,不得出現在
任何頂層 import。** 這樣 `run`/`serve`/`session`/`doctor` 的執行路徑完全不載入
Ink,啟動時間不受影響。作法與 `serve` 動態 import core 相同
(`cli_hld.md` §13.1),理由不同:那裡是為了環境變數順序,這裡是為了啟動成本。

驗收要有一條實測斷言:`deskmony run` 的 wall-clock 啟動時間在加入 TUI 前後
差異不超過 50ms。

## 6. 輸入處理

### 6.1 焦點模型

兩層,不做更複雜的:

- **窗格焦點**(Sessions ↔ Transcript):`Tab` / `Shift+Tab` 循環。
- **窗格內移動**:`↑↓` 在 Sessions 選 session;`↑↓`/`PageUp`/`PageDown` 在
  Transcript 捲動。

權限彈窗出現時**搶走全部按鍵**,底層窗格不接收——避免「以為在選 session,
其實按到了允許」。

### 6.2 裸 Esc 的處理

§1.4 量到裸 Esc 就是 `1b`,與 `1b 5b 41`(↑)的開頭無法區分。作法:收到 `1b`
後起一個 **30ms** 計時器,期間若沒有後續位元組就判定為裸 Esc;有的話當跳脫
序列解析。30ms 是本機終端的安全值(遠端 ssh 需要更長,但 TUI 跑在本機終端,
按鍵不經過網路)。

### 6.3 Ctrl+C

`03` 是位元組不是訊號(§1.4)。語意與 REPL 一致
(`apps/cli/src/commands/chat.ts`):

- 焦點 session 正在 busy → 第一次 = `session.interrupt`,並提示「兩秒內再按
  一次離開」
- 兩秒內第二次 → 離開 TUI
- 沒有 busy 的 session → 直接視為離開意圖,同樣要兩秒內按第二次確認

離開時**一定要還原終端**:退出 alternate screen、顯示游標、關閉 raw mode。
這三件事要放在同一個 `restore()` 函式,並掛在 `process.on("exit")`——否則
崩潰後使用者的終端會壞掉(看不到游標、鍵盤沒回顯),那是最惹人厭的 bug。

### 6.4 中文輸入

stdin 走 `new StringDecoder("utf8")`,不對每個 chunk 直接 `toString()`——
§1.4 量到 `中` 是 3 個位元組,chunk 邊界可能切在中間。

## 7. 效能:多 session 串流會燒掉終端機

這是多 agent TUI 特有的問題,單 session 的工具不會遇到。

`message-delta` 事件在一個 busy session 上可以每秒數十次;Deskmony 可以同時
有五個 session 在 busy。天真的「每個事件重繪一次」會變成每秒數百次全螢幕
重繪——終端機會卡死,而且**閃爍**。

紀律:

1. **事件進來只更新資料模型,絕不直接觸發重繪。**
2. 重繪走固定節奏:`setInterval` 33ms(約 30fps),有髒資料才畫。
3. **非焦點 session 的 delta 只累積、不參與重繪**——它們的內容根本沒顯示在
   畫面上。Sessions 窗格只需要知道「它還在動」,那是一個 spinner 幀,不是
   全文。
4. Transcript 的捲動緩衝**有上限**(每個 session 保留最後 2000 行),超過從
   頭砍。alternate screen 沒有終端機原生的 scrollback 可以退回去,緩衝就是
   全部——但無上限地留著會在跑數小時的 session 上吃掉記憶體,而那正是這個
   產品的預設使用情境。

## 8. 刻意不做的

| 不做 | 為什麼 |
|---|---|
| **滑鼠支援** | 開了滑鼠追蹤序列,多數終端機的「選取文字複製」就壞了。終端使用者對這件事的容忍度是零 |
| **PTY session 的終端輸出** | `terminal-data` 事件帶的是原始 ANSI(桌面端用 xterm.js 渲染)。在 TUI 的窗格裡渲染巢狀 ANSI 等於要內嵌一個終端機模擬器。TUI 顯示一行「這是 PTY session,請用 `deskmony chat --session <id>` 或桌面 app」 |
| **任務看板 / 團隊群聊** | 資料都拿得到(`task.list`/`team.messages`),但塞進同一個版面會讓每個東西都變小。等 §4 的權限佇列被實際用過再說 |
| **真.無限制層的開關** | `DECISIONS.md` §G 要求打字確認的儀式。它不該出現在一個為了「快速清佇列」而優化的介面裡 |
| **主題 / 設定檔** | 先讓它在預設狀態下好用 |

## 9. 檔案結構

```
apps/cli/src/
  commands/tui.ts        # 唯一的進入點,await import("../tui/app.js")
  tui/
    app.tsx              # Ink 根元件、狀態容器、33ms 重繪節奏
    model.ts             # 事件 → 資料模型(不含任何渲染)
    keys.ts              # 原始位元組 → 具名按鍵(含 §6.2 的 Esc 逾時)
    restore.ts           # alt screen / 游標 / raw mode 的還原,掛 process exit
    panes/
      SessionsPane.tsx
      TranscriptPane.tsx
      AlertBar.tsx
      StatusBar.tsx
      PermissionModal.tsx
    theme.ts             # 圖示與色碼(圖示不得用 emoji,見 §1.3)
```

`model.ts` 與 `keys.ts` **不 import Ink 或 React**——它們是純函式,可以在
e2e 裡直接單元測試,不需要跑起一個終端機。這是讓 TUI 可測的關鍵切法。

## 10. 怎麼驗收

TUI 的自動化測試比 CLI 難,誠實面對:能測什麼、不能測什麼要先講清楚。

### 10.1 能自動測(進 `scripts/e2e-cli-tui.mjs`)

用 `node-pty` 開真的 ConPTY 跑 `deskmony tui`,程式化送按鍵、改尺寸,再對
**輸出的位元組**做斷言(§1.4 已證實這條路可行)。

> **⚠ 寫斷言前先讀這段:不要天真地把 ANSI 濾掉再比對字串。**
> T1 驗收時我用 `s.replace(/\x1b\[[0-9;?]*[a-zA-Z]/g, "")` 過濾 ANSI,連續得到
> 三個**假的**失敗結論:
> 1. 「方向鍵沒作用」——實際上當時一個 session 都沒有,Ink 做完差異比對後
>    不送任何位元組,那是正確行為。**測導航一定要先建好 session。**
> 2. 「沒有選取指標」——指標 `▸` 是用反白呈現(`\x1b[7m▸\x1b[27m`),被濾掉了。
> 3. 「狀態列只有 65 欄、兩半擠在一起」——Ink **不是用空格補間隔**,而是
>    `\x1b[35X`(ECH,清除 35 格)加 `\x1b[35C`(CUF,游標右移 35 欄)。
>    把游標移動濾掉,35 欄的間隔就憑空消失了。實際版面是滿版 100 欄、正確。
>
> 結論:**游標移動序列(CUF/CUP)與 ECH 本身就是版面資訊,不是雜訊。** 斷言
> 要嘛用完整的終端機模擬器把畫面還原成字元格陣列再比對,要嘛只斷言
> 「某段文字有沒有出現」這種不依賴欄位位置的性質。不要用濾掉 ANSI 之後的
> 字串去推論寬度或對齊。

要涵蓋:

1. 啟動後畫面含 `Deskmony` 標題與 `SESSIONS`
2. 送 `\x1b[B`(↓)→ 焦點列變化
3. `term.resize(50, 12)` → 輸出含「終端機太小」;再 resize 回 100×30 → 版面回來
4. 觸發一筆 `ACP_WRITE_FILE` 權限請求 → alert bar 出現待決計數
5. 送 `a` → 權限彈窗出現,且**輸出中含 `input` 裡的檔案路徑**(§4.2 的紀律)
6. 送 `d`(拒絕)→ 彈窗消失,檔案未落地
7. 送 `\x03`(Ctrl+C)兩次 → 行程退出,**且輸出結尾含 `\x1b[?1049l`(離開 alt
   screen)與 `\x1b[?25h`(顯示游標)**——終端還原的斷言,不能只看有沒有退出
8. `model.ts` / `keys.ts` 的純函式單元測試(Esc 逾時、UTF-8 chunk 切半)
9. `deskmony run` 啟動時間回歸(§5.2)

### 10.2 不能自動測,要人看

- **§3 用到的整組圖示字元在真實終端機的字形渲染**(見 §1.2.1——目前只有細框線
  目視確認過,其餘只有帳面寬度)。T1 必須補這一張截圖,缺字就退回細框線。
- 實際的視覺品質(對齊、顏色、疏密)
- 真實終端機的閃爍程度
- 長時間跑(數小時)的記憶體行為

這幾項在 PR 裡用截圖交付,並明講「這是人看的,不是自動化把關的」。
