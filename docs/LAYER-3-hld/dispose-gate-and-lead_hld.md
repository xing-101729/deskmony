# S5 HLD:Lead(AgentProfile)+ dispose-gate(收斂閘)

> 階段:**Phase 2**(L3 最後一份)｜對應 L1:**A1、A2**｜上層:[L2 §3](../LAYER-2-design-spec.md)、[DECISIONS §A](../DECISIONS.md)
> 前置:[S8](./agent-lifecycle_hld.md)(Lead 長命=在線可達 + 外部記憶)、[S2](./message-budget_hld.md)(訊息受 context 預算)、[S4](./acceptance-gate_hld.md)(驗收閘)
> **L2 定案的關鍵定性**:**Lead 不是 Core 模組,是一個 AgentProfile**(prompt/設定)。Core 淨新增的只有一層薄的 **dispose-gate**。若把 Lead 寫成 Core 程式,會蓋出一套確定性編排引擎,**正好違反 A2「LLM 提議」**。

---

## 0. 現況(已查證)

`team-bus` MCP 已有:`send_message` / `broadcast` / `request_review` / `report_status` / `list_teammates`。

⚠️ **關鍵事實**:`report_status` **已經能直接推進任務狀態**(`tryApplyReportStatus`)——這就是「**agent 自我推進**」的既有路徑,**目前沒有任何收斂閘**。dispose-gate 要攔的正是它。

---

## 1. 職責邊界

**Lead(AgentProfile,非程式碼)負責**:
- **提議**任務拆解、指派對象、完成判定。全部是**提議**,不是決定。
- 協調隊友(送訊息、請求 review)、維護外部記憶(S8 §2.1)。

**dispose-gate(Core,薄層)負責**:
- 攔截**收斂型提議**,要求人/規則核可才生效,通過的才轉成 TaskService 動作。

**不負責**:
- ❌ 確定性的排程/編排演算法(那會違反 A2)。
- ❌ 訊息路由(→ S2)、生命週期(→ S8)。

---

## 2. 發散 vs 收斂:閘該攔什麼(A2 的落地)

### 2.1 判準是「不可逆性」,不是「有無副作用」(S5 grill 定案)

草稿把「指派」歸為收斂要過閘,理由是「它有副作用(建 worktree、spawn worker)」。**這個判準是錯的,而且會讓 Lead 失去存在意義**:

> 若 Lead 每次指派都要人核可 → 無人值守時 Lead 拆解完想指派 → 掛起等你 → 你在睡覺 → **整個團隊停擺**。而 Lead 存在的唯一理由就是「讓你不必逐一調度」。**一個每次調度都要問你的 Lead,價值等於零。**

而且**副作用 ≠ 不可逆**:指派錯了,退回任務、刪 worktree 即可,**沒有任何東西被永久破壞**。真正不可逆的只有「合併進主幹」。

**定案:只有「不可逆或難撤銷」才過閘。**

| Lead 的動作 | 可撤銷? | 閘? |
|---|---|---|
| 提議拆解、送訊息、請求 review、讀寫記憶 | — | ❌ 自由(受 S2 訊息預算) |
| **定案拆解**(建立子任務) | ✅ 可刪 | ❌ **自由** |
| **指派任務給 worker** | ✅ 可退回、可刪 worktree | ❌ **自由** |
| **判定任務完成**(`report_status(done)`) | — | ✅ **規則裁決**(§2.2) |
| **批准合併**(`review → merging`) | ❌ **改動主幹,難撤銷** | ✅ **人類必核** |

- **與整份設計的判準一致**:C5 的硬性 deny 類挑的正是「不可逆或會外洩」的操作,不是「所有有副作用的」。**權限層都用不可逆當標準,收斂閘沒理由更嚴。**
- **讓 Lead 真的有價值**:能自主拆解與調度(可撤銷),但碰不到主幹(不可逆)。正是 A1 階層骨架要的——**worker 可拋棄、調度可自主、主幹要人守**。
- 撤銷路徑是**既有能力**,不是空話:狀態機有 `review → in-progress` 退回、worktree 有清理、S6 有分流視圖。
- ⇒ **閘變得非常薄**,符合 L2「Core 淨新增的只是薄的 dispose-gate」。

### 2.2 判定完成:有 acceptance 才可機器自動放行(S5 grill 定案)

§2.1 放行了指派與拆解,所以**唯二的守門是 S4 驗收 + 人類合併核可**。但 S4 已定案是「**快篩,不是證明**」(agent 能閹割測試繞過)。故不能單靠「S4 過就放行」:

| 任務有 `acceptance` 條件? | 裁決 |
|---|---|
| **有** | **機器判**:S4 驗收過 → 自動放行進 review;不過 → 拒絕 |
| **無** | **人判**:掛起等人核可(無人值守時同 S11 §4 語意,不 deny) |

- **讓 S4 的「可選」設計產生真正的後果**:有驗收條件 = 你已預先定義「怎樣算過」→ 機器可代你判;沒有 = 你沒告訴系統標準 → **只能你自己判**。誠實且自洽,也正是 **A3 的例外條款**。
- **給了定義驗收條件的正向誘因**:想要 agent 自主推進?就寫驗收條件。**紀律靠誘因,不靠強制**。
- **S4 快篩的弱點由下游兜底**:即使閹割測試混過 review,**合併仍需人核可**(§2.1)——那才是正確性的最後防線。

## 3. dispose-gate 的三種裁決模式

閘不是只有「問人」一種。依動作風險分級:

| 模式 | 用於 | 行為 |
|---|---|---|
| **規則自動核可** | 有 `acceptance` 的完成判定 | 過 S4 驗收 → 自動放行,不必問人(§2.2) |
| **人類核可** | **不可逆**:批准合併(**永遠人核可**);無 `acceptance` 的完成判定 | escalate 等人 |
| **拒絕** | 違反硬規則 | 非法狀態轉換、指派給不存在的 member、S4 驗收未過 |

- **這正是 A2「人/規則裁決」的兩條腿**:規則能判的用規則(不打擾人),規則判不了的才升級給人。
- **升級走共用底座**(同 S1 的 `escalate`):發事件 → S11 通知 → 人回覆。**重用,不新建**。
- **無人值守時**:沿用 S11 §4 的語意——不 deny,**掛起等人**,由 S3b 的 T1/T2 兜底。

## 4. Lead 是 AgentProfile:它的「程式」是 prompt

Lead 的能力來自三樣東西,**沒有一樣是新的 Core 程式**:

| 元素 | 內容 |
|---|---|
| **systemPrompt** | 定義它是協調者:如何拆解、何時指派、何時請求 review、**必須把決策理由寫進外部記憶** |
| **工具** | 既有的 team-bus 工具(`send_message`/`report_status`/`list_teammates`…)+ 檔案工具(讀寫記憶) |
| **設定** | `lifecycle: persistent`(S8:在線可達)、`canInterrupt: true`(既有欄位,協調者可打斷 worker) |

> **S5 的 HLD 主體因此是「prompt 契約 + 哪些提議要過閘」,不是排程演算法**(L2 定案)。

### 4.1 不新增 `propose_*` 工具:閘掛在狀態轉換上(S5 grill 定案)

| 做法 | 判定 |
|---|---|
| 新增 `propose_breakdown` / `propose_merge` 等工具 | ❌ 新增 agent 要學的介面,且**既有工具仍在** → 製造「舊工具能否繞過」的問題 |
| **不新增,閘在下游攔截** | ✅ **採用** |

- **與 S4 完全同構**:S4 的驗收閘也掛在同一條轉換路徑上,不是新增工具。**同一位置、同一模式**,兩者自然合併成一條閘鏈。
- **無法繞過**:狀態轉換是唯一入口(§6)。
  > ⚠️ **L4 精確化**([S4 L4 §0.1](../LAYER-4-detail-design/acceptance-gate_detail.md)):閘應收斂到 **gateway 的 `task.updateStatus` 這個唯一對外入口**,**不是** `TaskService.updateStatus()` 內部——既有程式碼(task-service.ts L29–42)刻意讓 `updateStatus()` 只管「轉換合不合法」、不承擔語意檢查。語意等價且不破壞分層。
- **agent 介面零變動**:Lead 用的還是 `report_status`,只是**回應可能是「已提交待核可」而非「已生效」**——這個語意變化足以讓 Lead 理解發生了什麼。
- ⇒ S5 的**淨新增程式幾乎只剩「在 TaskService 狀態轉換上加一層裁決」**,與 S4 共用攔截點。印證 L2「Core 淨新增的只是薄的 dispose-gate」。

## 5. 資料流

```
Lead(LLM)呼叫既有 team-bus / TaskService 工具   ← 工具介面零變動(§4.1)
   │
   ├── 可撤銷(拆解、指派、訊息、記憶) ──────> 直接生效(受 S2 預算)
   │
   └── 完成判定 / 批准合併
            │
            ▼  dispose-gate(掛在 TaskService 狀態轉換上,與 S4 同一攔截點)
       ┌────┴──────────┬──────────────┐
   有 acceptance?    批准合併        違規
       │                │              │
   S4 驗收過→放行    永遠 escalate    拒絕
   無 acceptance→     (S11 通知)    + 明確錯誤回 Lead
     escalate 等人
            │
            ▼
      TaskService 動作生效
```

## 6. 失敗模式

| 情境 | 行為 |
|---|---|
| Lead 做出爛拆解 / 爛指派 | **閘不擋**(§2.1 可撤銷)——由人在群聊/看板看到後**退回重來**,或由驗收閘與 merge-review 在下游攔截成果。刻意接受「拆解可能爛」以換取 Lead 的自主價值。 |
| Lead 反覆提交被拒的提議 | 拒絕理由明確回傳;高頻重試觸發通知(同 S2 §6)。 |
| Lead 繞過閘直接呼叫 `report_status` | **不可能**——閘掛在 TaskService 的狀態轉換上,是唯一入口(同 S4 的作法)。 |
| Lead 自己判定自己的任務完成 | 仍須過 S4 驗收 + 閘;**A2 明令禁止同一 LLM 既拆解又自評**。 |
| Lead 崩潰/context 重啟 | S8 §2.2 checkpoint 重啟;in-flight 的待核可提議留在閘上,不隨 Lead 消失。 |
| 沒有 Lead 的團隊 | 完全合法——人類自己扮演 Lead(切片/Phase 1 就是如此)。**Lead 是可選的**。 |

## 7. 對應 L1 決策

**A1**(階層骨架 + peer 橫向)· **A2**(LLM 提議、人/規則裁決;禁止同一 LLM 既拆解又自評)· 與 **S4**(驗收作為規則裁決的一條腿)、**S8**(Lead 長命/外部記憶)、**S2**(訊息預算)、**S1/S11**(共用升級底座)協同。

## 8. 開放問題(留給 L4)

1. **prompt 契約的具體內容**:如何讓 Lead 穩定地拆解、指派、並把決策理由寫進外部記憶(S8)。
2. **合併核可的 UX**:Lead 請求合併時人看到什麼(diff 摘要?驗收結果?);多個待核可合併如何批次處理。
3. **Lead 的 `canInterrupt` 是否該有配額**(S2 §8.3 的相關開放問題)。
4. **多 Lead / 無 Lead 的團隊**:是否允許?角色衝突如何處理?
5. **「已提交待核可」的回應語意**:如何讓 Lead 正確理解並且不重複提交。
