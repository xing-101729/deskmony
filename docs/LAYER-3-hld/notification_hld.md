# S11 HLD:Notification(升級/熔斷的帶外送達)

> 階段:**Phase 1**｜對應 L1:新增(無人值守帶外通知,支撐 §C/§E 的 escalate/trip)｜上層:[L2](../LAYER-2-design-spec.md)
> 前置:[S1 HLD](./policy-engine_hld.md)(定義 `Notifier` 底座介面與 `EnforcementEvent`)。
> **定位**:S11 是 Enforcement 共用底座的**送達端實作**。S1 §4.1 已證明 Phase 1 會**頻繁 escalate**,故通知不是配角——**它是 Phase 1 無人值守能否成立的關鍵路徑**。

---

## 0. 現況(已查證)

**專案內完全沒有任何人類通知機制**——沒有系統通知、沒有 webhook、沒有 tray。S11 是純新建模組。

> 這揭示一個結構性缺口:目前的設計裡,agent 卡住等權限時,**沒有任何東西會告訴你**;你不在螢幕前,它就靜靜等到 5 分鐘逾時被 deny。**無人值守的整個前提是「你不在看」,而現況沒有任何把你叫回來的管道。**

---

## 1. 職責邊界

**負責**:
- 實作底座的 `Notifier.deliver(e: EnforcementEvent)`。
- 兩條通道:**桌面系統通知**(你在電腦前)+ **webhook**(你不在,如 Slack/Discord)。
- 通道選擇、去重/節流、失敗處理。

**不負責**:
- ❌ 決定「什麼事該通知」(那是 S1/S3b/S2 產生 `EnforcementEvent` 時決定的)。
- ❌ 稽核落地(底座 `AuditLog`)。
- ❌ **回覆的接收**——人類要核可,是透過 UI/遠端 client 回到 Gateway(見 §3),**不是**回覆 webhook 訊息。

---

## 2. 通道模型

| 通道 | 何時用 | 內容 |
|---|---|---|
| **桌面系統通知** | 桌面 app 執行中 | 標題 + 摘要,點擊聚焦到對應 session |
| **Webhook**(Slack/Discord/任意 HTTP POST) | 一律送(可設定只在無人值守時送) | 摘要 + **深連結**(見 §3) |

**設計立場(DECISIONS F 的延伸)**:webhook 讓你人在外面也會被叫回來 → 你會想從手機開遠端 client(隧道後)去核可。**通知與遠端是配套的**:通知負責「叫你」,遠端 client 負責「讓你能回應」。

---

## 3. 回應路徑:通知只是「叫你」,不是「讓你核可」

```
escalate/trip 發生
   → Notifier.deliver()  ──> 桌面通知(點擊 → 聚焦 session)
                         └─> webhook  ──> 訊息含深連結
                                            │
                                    人打開 UI / 遠端 client(隧道後)
                                            │
                                    在 Gateway 上做決策  ★ 唯一的授權入口
```

**硬規則**:
- **絕不**在 webhook 訊息裡提供「一鍵允許」按鈕或回覆式核可。理由:Slack/Discord 訊息通道**不是**經過認證的授權通道;任何能看到那個頻道(或偽造 webhook 回呼)的人就能核可 agent 的危險操作,等於在安全罩上開一個後門。授權**只能**經 Gateway 的認證連線(F3/F4)。
### 3.1 內容最小化:只帶元資料,不帶內容(S11 grill 定案)

webhook 端點是**外部服務**——送出即離開你的機器,可能被索引、被同頻道的人看到、被留存。定案規則:**通知只帶「元資料」,不帶「內容」**。

| | 項目 |
|---|---|
| ✅ **可帶** | session/agent 名、工具名(Bash/Write/Read)、待決數量、事件種類(escalate/trip)、時間 |
| ❌ **不帶** | 指令字串、檔案路徑、檔案內容、agent 輸出、錯誤訊息全文、任何 config/env 值 |
| ⭐ **trip 例外** | 可多帶「原因分類」(如「成本上限」「訊息熔斷」)——是判斷急迫性的關鍵,且分類本身不含敏感內容 |

範例:`Coder-1:等待核可 Bash ×2、Write ×1` + 深連結。你能判斷急迫性,但看不到具體內容;要看細節就走深連結回到認證通道。

> 這與 §3「授權只經 Gateway」是同一原則的延伸:**外部通道只承載足以叫你回來的資訊,不承載工作內容。**

---

## 4. escalate 的逾時語意(S11 grill 定案 — 反向修正 S1)

**發現的結構性矛盾**:S1 原本定「escalate 逾時 5 分鐘 → deny(fail-safe)」。但**無人值守的前提就是你不在**(睡覺/開會/通勤)——5 分鐘幾乎必然逾時,等於宣告「**無人值守時所有 escalate 最終都 deny**」,半夜整排任務卡死,早上回來全是 blocked。「沒人回應」被錯誤地解讀成「拒絕」。

**定案:逾時語意情境相依**(修正 [S1 §6](./policy-engine_hld.md)):

| 情境 | 逾時行為 |
|---|---|
| **attended(有人看)** | 維持短逾時 → **deny**。你就在旁邊,5 分鐘不理 = 你不想要。 |
| **無人值守** | **不 deny**,轉為掛起 `waiting-permission`,session 不推進、不佔資源。人回來即繼續。 |

- **安全性不受損**:掛起 = 什麼都沒執行,和 deny 一樣安全,只是**保留了你回來後繼續的可能**。
- **真正的止損交給預算**:掛起的 session 不燒 token;若你三天不理,任務層的成本/時間預算(S3b)會叫停它。**「叫停」由預算負責,不由權限逾時負責**——呼應 L1 三斷路器各司其職。

## 4.1 節流:目標是「保住通知的可信度」

上節解除了逾時壓力,故原本「節流窗必須 ≪ 5 分鐘」的緊箍咒**消失**。節流現在要解決的是**通知疲勞**——你被 ping 太多次就會關掉通知,**那才是真正毀掉安全網的失敗模式**。

> **設計目標(定案)**:節流的目的不是趕上逾時,而是**保住通知的可信度——讓每一則通知都值得看**。

| 機制 | 規則 |
|---|---|
| **批次彙總** | escalate 累積成批,以**較長間隔**推送(預設 15–30 分,可設):「Deskmony:3 個操作等待核可」。等待不再有懲罰,故可從容。 |
| **去重** | 同一 session 連續同類請求只計一次,直到人回應。 |
| **分級** | `trip`(熔斷,已叫停)**必送、不節流、不併批**——事情已經停了,漏掉損失最大。 |
| **靜音窗** | 只壓 escalate,**不壓 trip**。 |

## 5. 設定(config.json,agent 不可寫)

```ts
notification: {
  desktop: { enabled: boolean },
  webhook: { url: string, enabled: boolean, minSeverity: "escalate" | "trip" },
  quietHours?: { from: string, to: string },
}
```

- **webhook URL 是敏感值**——它是「能對外送資料」的能力。config loader 現況已拒收憑證欄位;webhook url 需比照處理(不隨 gateway 查詢回傳給遠端 client)。
- **agent 不可寫**(同 C3 紀律):否則 agent 能改 webhook url 把資料外送到任意端點,或關掉通知讓自己不被監督。

---

## 6. 失敗模式

| 情境 | 行為 |
|---|---|
| webhook 送出失敗(網路/服務掛) | 記稽核「未送達」;**不重試到天荒地老**(有限次退避)。**不因通知失敗而放行**——attended 逾時仍 deny;無人值守仍掛起(§4)。 |
| 桌面 app 未執行 | 只走 webhook。 |
| 兩條通道都不可用 | 事件仍落稽核 log;attended → 逾時 deny,無人值守 → 掛起。**系統安全地停,不危險地放行。** |
| webhook 端點被改成惡意位址 | 由「agent 不可寫 config」防護(§5);遠端亦不可改(F3)。 |
| 通知風暴(大量 escalate) | §4 節流合併;若仍超量,退化為「每 N 分鐘一則彙總」。 |

---

## 7. 對應 L1 決策

- 支撐 **C2 default-deny**:default-deny 會產生 escalate,沒有通知就沒有人能回應 → S11 是 C2 在無人值守下可用的前提。
- **E2/E3**(成本熔斷)與 **A5**(訊息熔斷)的 `trip` 送達端。
- **F3/F4**:授權只經 Gateway;webhook 不是授權通道;webhook 設定遠端不可改。
- **D5**:所有送達與失敗都進稽核 log。

---

## 8. 開放問題(留給 L4)

1. **批次間隔預設值**:15 分?30 分?(§4.1 已解耦逾時,純看通知疲勞。)
2. **`waiting-permission` 掛起的上限**:由 S3b 的任務時間/成本預算叫停,具體 TTL 待 S3b 定。
3. **深連結格式**:桌面 app 的 custom protocol(如 `deskmony://session/<id>`)?遠端 client 的 URL 形式?
4. **是否支援多個 webhook**(如工作/私人各一)?
5. **trip 是否需要獨立的更強通知**(如重複推送直到確認)?

---

> **S11 grill 已完成(2026-07-24)**,3 項定案:
> ① **escalate 逾時語意情境相依**(反向修正 S1 §6):attended → 短逾時 deny;**無人值守 → 掛起 `waiting-permission`,不 deny**。「沒人回應 ≠ 拒絕」;止損改由預算(S3b)負責,不由權限逾時負責。
> ② **節流目標 = 保住通知可信度**(非趕逾時):escalate 批次彙總、間隔可長;**trip 必送不節流**。
> ③ **內容最小化 = 只帶元資料不帶內容**;trip 可多帶原因分類。外部通道只承載「叫你回來」的資訊。
